# Правила работы с репозиторием

Эти правила обязательны для всех участников Team MedBase. Короткая версия продублирована в [README.md](README.md#правила-работы-с-репозиторием).

## 1. Ветка `main` всегда готова к демо

В любой момент из `main` должно быть можно показать корректно работающий проект.

`main` считается готовой к демо, если на чистой базе:

1. база собирается с нуля (`docker compose`, пустой volume);
2. автотесты проходят (в конце `ALL TESTS PASSED`);
3. `db/demo.sql` отрабатывает до конца без сломанного SQL;
4. `db/05_queries.sql` выполняется, а `db/setup.sql` можно запустить повторно.

Всё это проверяет одна команда. Запустите её у себя перед открытием PR (в Git Bash на Windows):

```bash
bash scripts/check-db.sh
```

В конце должно быть `OK: database is demo-ready`. Скрипт пересоздаёт локальную базу (`docker compose down -v`), поэтому данные, введённые вручную, пропадут.

**CI.** Та же проверка автоматически запускается на GitHub (workflow `.github/workflows/db.yml`, проверка `db-check`) на каждый PR в `main` и на каждый push в `main`. PR с красной проверкой слить нельзя. Если CI упал, откройте вкладку Actions, найдите упавший шаг и исправьте ошибку в своей ветке: новый push перезапустит проверку.

Пока CI проверяет только базу данных. Проверки для новых компонентов добавляются по решению `theleriz`. Новый компонент должен иметь свою проверку, прежде чем от него будет зависеть демо.

- Незаконченная или непроверенная работа в `main` не попадает: она живёт в своей ветке, пока не пройдёт проверку.
- Новая таблица, процедура или правило добавляются вместе с тестами в `db/tests/test_hospital_ward.sql`. Если меняется поведение, которое видно в демо, обновляется `db/demo.sql`.
- Если `main` сломалась, её починка важнее любой другой работы.

## 2. Все изменения — через Pull Request

- Любое изменение (код, SQL, документы) попадает в `main` только через Pull Request (PR).
- Прямой push в `main` запрещён.
- PR сливается только при зелёной проверке CI `db-check`.
- **Сливает PR в `main` только `theleriz`** (zanatrisat54@gmail.com). Участники открывают PR, а `theleriz` проверяет его и сливает.
- **Исключение:** только `theleriz` может пушить в `main` напрямую. Правило 1 действует и для него.
- В описании PR указывается, что изменено и как это проверить. Перед тем как просить о слиянии, автор отмечает чек-лист из шаблона PR.

Эти ограничения закреплены на GitHub правилами ветки (Settings → Rules → Rulesets → «main: PR only, demo-ready»): изменения только через PR, обязательная проверка `db-check`, запрет force push и удаления `main`; обходить правила может только админ репозитория.

## 3. Начинать работу от свежей `main`

Перед началом работы над новой функциональностью или новым документом обновите `main` и создайте ветку от неё, чтобы не было рассинхрона:

```bash
git checkout main
git pull origin main
git checkout -b feature/doctor-table
```

Именование веток:

| Префикс | Для чего | Пример |
|---|---|---|
| `feature/` | новая функциональность | `feature/bed-table` |
| `fix/` | исправление ошибки | `fix/ward-capacity-check` |
| `docs/` | документы и описания | `docs/task-10-report` |

Если пока вы работали, `main` ушла вперёд, подтяните её в свою ветку перед открытием PR:

```bash
git checkout main
git pull origin main
git checkout feature/doctor-table
git merge main
```

## Документы

Документы подчиняются тем же трём правилам, что и код: ветка от свежей `main` (префикс `docs/`) и PR.

### Работы участников — `docs/works/`

- У каждого участника своя папка `docs/works/<Фамилия>_<Имя>/`, например `docs/works/Zhanat_Rishat/`.
- Файлы называются `<StudentID>_<Фамилия>_<Имя>_Task<N>.docx`, например `24B031775_Zhanat_Rishat_Task2.docx`.
- Каждый кладёт файлы только в свою папку.

```bash
git checkout main
git pull origin main
git checkout -b docs/zhanat-rishat-task8
# положить файл в docs/works/Zhanat_Rishat/
git add docs/works/Zhanat_Rishat/24B031775_Zhanat_Rishat_Task8.docx
git commit -m "Add Task 8 (Zhanat Rishat)"
git push -u origin docs/zhanat-rishat-task8
# открыть PR на GitHub
```

### Критические решения — `docs/decisions.md`

- Сюда записываются только критические решения: смена технологии, способ работы с чем-то важным и т. п. Мелкие решения, которые не влияют на проект, сюда не пишутся.
- Каждая запись оформляется по шаблону из начала файла. Номера идут по порядку: 1, 2, 3…
- Новая запись добавляется в конец файла.
- Старые записи не переписываются. Если решение поменялось, добавляется новая запись, а в её поле `Reference` указывается номер прежней.
