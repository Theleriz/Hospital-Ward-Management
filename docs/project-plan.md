# План проекта: Hospital Ward Management System

Описывает, к какой системе мы идём, что в неё входит и что нет, на какие этапы делится разработка и кто за что отвечает.

Требования ко времени оповещения и границы MVP зафиксированы в [decisions.md](decisions.md) (записи 1–3). Решения, которые меняют этот план (стек, границы, сроки), записываются туда же.

## 1. Где мы сейчас

Что уже есть:

- **База данных PostgreSQL** (`db/`): `Patient`, `Ward`, `Admission`, `WardAlert`; процедуры госпитализации, перевода, регистрации с госпитализацией и подтверждения оповещения; роли `medbase_admissions` и `medbase_public_staff`; 43 автотеста; пошаговое демо.
- **Инфраструктура**: Docker Compose, CI-проверка `db-check`, правила работы с репозиторием.
- **Решения из лабораторных** (Task 5–7), на которые опирается система:
  - оповещение должно появиться на экране поста медсестры **не позже чем через 2 секунды** (NFR-01, Lab 5);
  - неподтверждённое оповещение HIGH/CRITICAL через **30 секунд** уходит второй медсестре со статусом Available (Lab 6, Lab 7);
  - приоритеты только `LOW`, `HIGH`, `CRITICAL`; журнал оповещений и подтверждений — главный источник данных при разборе инцидентов (Lab 6, Lab 7);
  - вход медсестры по бейджу, запасной вариант — логин и PIN (Lab 5);
  - сеть только внутренняя, сервер принимает подключения только с известных рабочих мест; резервное копирование важнее файрвола (Lab 6).

Чего нет (исправляется по ходу разработки, задачи этапа 1):

- приложения (backend и интерфейса) — сейчас с системой можно работать только через SQL;
- медсестёр как сущности: `WardAlert."NurseID"` — просто строка без внешнего ключа, нет статуса Available, нет назначения медсестёр на палаты;
- эскалации, выписки пациента, времени реакции на оповещение. Сейчас `sp_AcknowledgeAlert` затирает `NurseID`, поэтому теряется, кому было назначено оповещение и кто его подтвердил;
- требований и критериев приёмки в виде документов;
- роли для медсестёр. Кроме того, `sp_AcknowledgeAlert` может выполнить любой пользователь (`PUBLIC`).

## 2. Видение: к чему мы идём

**Hospital Ward Management System** — информационная система одного отделения больницы. Она закрывает два процесса:

1. **Коечный фонд.** Приёмное отделение регистрирует пациента, кладёт его в палату, переводит и выписывает. Система не даёт положить пациента в заполненную палату или в две палаты сразу. Остальной персонал видит только занятость палат, без данных пациентов.
2. **Оповещения медсёстрам.** Монитор пациента или кнопка вызова создаёт оповещение. Система определяет приоритет и медсестру, которая отвечает за палату, и за 2 секунды показывает оповещение на экране поста. Медсестра входит по бейджу и подтверждает оповещение. Если HIGH/CRITICAL не подтверждено за 30 секунд, оно уходит свободной медсестре. Каждый шаг пишется в журнал, по которому старшая медсестра видит время реакции и эскалации.

**Результат к защите:** одна команда `docker compose up` поднимает базу, backend и веб-интерфейс. На демо мы проходим полный сценарий в браузере: госпитализация → оповещение от симулятора монитора → подтверждение или эскалация → отчёт по времени реакции.

### Пользователи

| Пользователь | Что делает в системе |
|---|---|
| Сотрудник приёмного отделения / врач | регистрирует, госпитализирует, переводит, выписывает пациентов |
| Медсестра отделения | видит оповещения своей палаты, подтверждает их, меняет свой статус (Available / Busy) |
| Старшая медсестра | смотрит журнал оповещений, время реакции, эскалации |
| Прочий персонал | видит только занятость палат |
| Администратор | заводит палаты и персонал (в MVP — через seed-данные) |

## 3. Границы системы

Зафиксированы в [decisions.md](decisions.md), записи 2 и 3.

### Входит (MVP)

- Сценарии UC-1 — UC-8.
- База данных: текущая схема плюс медсёстры, назначения на палаты, расширенное оповещение, журнал событий оповещения, выписка, эскалация.
- Backend (FastAPI) с бизнес-логикой, проверками и защитой; процедуры и ограничения БД — второй, независимый слой защиты ([decisions.md](decisions.md), запись 5).
- Веб-интерфейс: экран приёмного отделения, табло занятости, экран поста медсестры, панель старшей медсестры.
- Симулятор монитора и кнопки вызова: скрипт или кнопка, которая создаёт оповещения, как это делало бы реальное устройство.
- Вход по ID бейджа (поле ввода вместо RFID-считывателя) и PIN; доступ по ролям.
- CI: проверка БД, тесты backend, e2e-тесты главных сценариев.
- Документы: требования, критерии приёмки, архитектура и безопасность, словарь данных, отчёт о тестировании, журнал решений.

### Не входит

| Что | Почему / чем заменяем |
|---|---|
| Реальные мониторы пациентов и кнопки вызова | заменяем симулятором |
| Реальный RFID-считыватель | вводим ID бейджа в поле (считыватель USB-HID ведёт себя как клавиатура, так что подключить его потом несложно) |
| Мобильное приложение и MFA на телефоне | только веб-интерфейс; MFA описывается в документе по безопасности (Lab 6) |
| Медицинская карта, диагнозы, лекарства, анализы | вне задачи отделения |
| Оплата, страховка, бухгалтерия | вне задачи |
| Составление графика смен | смены и назначения задаются seed-данными, в интерфейсе только статус Available / Busy |
| Несколько больниц или отделений, доступ из интернета | одна установка во внутренней сети |
| Интеграции HL7 / FHIR | вне MVP |
| Файрвол, реальная инфраструктура бэкапов | описываем в документах; из бэкапа в MVP возможен только скрипт `pg_dump` (Could) |

Любое расширение границ — через новую запись в `decisions.md`.

| ID | Требование | Как проверяем |

| NFR-06 | `main` всегда готова к демо | CI на каждый PR (уже есть для БД) |

## 4. Архитектура

```
 Симулятор монитора / кнопки вызова
              │  POST /alerts
              ▼
 ┌─────────────────────────────┐        ┌──────────────────────┐
 │ Backend (REST API)           │◄──────►│ PostgreSQL           │
 │  • вход: бейдж / PIN, роли   │  SQL   │  таблицы, процедуры, │
 │  • API госпитализаций        │        │  роли, журнал        │
 │  • API оповещений + поток    │        └──────────────────────┘
 │    событий (SSE / WebSocket) │
 │  • фоновая эскалация (≈2 с)  │
 └──────────────┬──────────────┘
                │ HTTP + поток событий в реальном времени
                ▼
 React: приёмное отделение · табло палат · пост медсестры · старшая медсестра
```

**Стек** ([decisions.md](decisions.md), запись 4):

- **Интерфейс:** React.
- **Backend:** Python 3.12 + FastAPI + psycopg 3.
- **База данных:** PostgreSQL.
- **Тесты:** SQL-тесты (есть), pytest для backend, Playwright для e2e.

**Два слоя защиты** ([decisions.md](decisions.md), запись 5):

- **Backend** — основной слой: бизнес-логика, проверки, вход, роли и права доступа.
- **БД** — независимая подстраховка: критичные операции проходят через процедуры, которые вместе с ограничениями и правами ролей повторно проверяют правила. Ошибка в backend не приводит к некорректным данным.
- Слои не полагаются друг на друга, и каждый покрыт своими тестами.
- **Эскалация:** фоновый процесс backend каждые ~2 с находит просроченные оповещения и выбирает свободную медсестру, а процедура БД перед записью ещё раз проверяет, что эскалация допустима.

Стек можно усложнять по ходу проекта; каждое такое изменение — новая запись в `decisions.md`.
