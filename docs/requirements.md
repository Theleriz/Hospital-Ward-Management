## 1. Purpose and Scope

The Hospital Ward Management System is a web-based information system for one hospital ward.

The system supports two main processes:

1. Patient admission and ward capacity management.
2. Nurse alerts, acknowledgements, escalation, and reporting.

The purpose is to prevent incorrect patient admissions, improve alert handling, and provide reliable information to authorized hospital staff.

The Minimum Viable Product (MVP) covers eight use cases (UC-1 to UC-8).

### 1.1 Included in the MVP

- Patient registration, admission, transfer, and discharge.
- Ward occupancy monitoring.
- Nurse login using badge ID and PIN.
- Patient-care alerts generated by a simulator.
- Alert acknowledgement and escalation.
- Alert event logging and response-time reporting.
- Role-based access control.
- A web interface connected to a PostgreSQL database.

### 1.2 Excluded from the MVP

- Real patient monitors and physical call buttons.
- Physical RFID badge readers.
- Mobile applications and phone-based MFA.
- Electronic medical records, diagnoses, medications, and laboratory results.
- Payments, insurance, and accounting.
- Shift scheduling.
- Multiple hospitals and internet-facing deployment.
- HL7/FHIR integrations.
- Production firewall and backup infrastructure.

Real medical devices are replaced by a simulator. Badge IDs are entered through the web interface.

## 3. Functional Requirements

Each functional requirement describes a specific behavior of the system.

### UC-1 — Patient Registration and Admission

**FR-01:** The system shall allow authorized admissions staff to register a patient with a required FullName and DOB, and optional Phone and Gender fields.

**FR-02:** The system shall admit a registered patient to a selected ward only when that ward has available capacity.

**FR-03:** The system shall reject an admission when the selected ward is full and display an appropriate error message.

**FR-04:** The system shall prevent a patient from having more than one active admission at the same time.

### UC-2 — Patient Transfer

**FR-05:** The system shall allow authorized admissions staff to transfer an admitted patient to another ward when the destination has available capacity.

**FR-06:** The system shall close the previous active admission and create the new active admission within one database transaction.

**FR-07:** The system shall preserve the patient's current admission when the transfer fails.

### UC-3 — Patient Discharge

**FR-08:** The system shall allow authorized admissions staff to discharge a currently admitted patient.

**FR-09:** The system shall record the discharge date and change the admission status to Discharged.

**FR-10:** The system shall reject a discharge request when the patient has no active admission.

### UC-4 — Ward Occupancy

**FR-11:** The system shall display each ward's capacity, current occupancy, and available beds.

**FR-12:** The system shall calculate available beds using ward capacity minus the number of active admissions.

**FR-13:** The system shall allow other hospital staff to view ward occupancy without displaying patient personal information.

### UC-5 — Alert Creation and Display

**FR-14:** The system shall allow the patient-monitor or call-button simulator to generate an alert for a ward.

**FR-15:** The system shall assign each new alert one of three priorities: LOW, HIGH, or CRITICAL.

**FR-16:** The system shall identify the nurse assigned to the ward and associate that nurse with the alert.

**FR-17:** The system shall display new alerts on the nurse-station interface.

**FR-18:** The system shall provide an audible notification for HIGH and CRITICAL alerts.

### UC-6 — Nurse Login and Alert Acknowledgement

**FR-19:** The system shall authenticate a nurse using a badge ID and PIN.

**FR-20:** The system shall reject invalid login credentials without revealing whether the badge ID or PIN was incorrect.

**FR-21:** The system shall allow an authorized nurse to acknowledge an assigned or escalated alert.

**FR-22:** The system shall record the nurse who acknowledged an alert and the acknowledgement timestamp.

**FR-23:** The system shall allow a nurse to change their availability status between Available and Busy.

### UC-7 — Alert Escalation

**FR-24:** The system shall escalate an unacknowledged HIGH or CRITICAL alert to another Available nurse no earlier than 30 seconds and no later than 35 seconds after alert creation.

**FR-25:** The system shall not automatically escalate LOW-priority alerts.

**FR-26:** The system shall record the escalation recipient and timestamp.

**FR-27:** The system shall prevent escalation to a nurse whose status is Busy or OffShift.

### UC-8 — Head Nurse Reporting

**FR-28:** The system shall allow the head nurse to view alert history.

**FR-29:** The system shall calculate alert response time using the acknowledgement timestamp minus the creation timestamp.

**FR-30:** The system shall display the number of escalated alerts in the reporting interface.

**FR-31:** The system shall restrict access to detailed alert reports to authorized roles.

## 4. Non-Functional Requirements

| ID | Requirement | Verification Method |
|---|---|---|
| NFR-01 | The system shall display a newly created alert on the nurse-station screen within 2 seconds. | End-to-end test measuring the time from simulator alert creation to screen display. |
| NFR-02 | The system shall escalate an unacknowledged HIGH or CRITICAL alert after 30 seconds, with a testing tolerance of up to 5 additional seconds. | Backend test with an accelerated timer and manual demonstration. |
| NFR-03 | The system shall prevent other hospital staff from accessing patient personal data. | SQL permission tests and backend tests expecting HTTP 403 for unauthorized access. |
| NFR-04 | The system shall prevent application roles from updating or deleting existing alert event log entries. | SQL permission tests attempting UPDATE and DELETE operations. |
| NFR-05 | The complete system shall start using one Docker Compose command on a clean development machine. | Start all services from a clean environment and verify database, backend, and frontend availability. |
| NFR-06 | The main branch shall remain demonstrable after accepted changes. | Run required CI checks on each Pull Request before merging. |

## 5. Business Rules and Constraints

**BR-01 — Ward Capacity:** A ward must have a capacity greater than zero.

**BR-02 — Admission Limit:** A patient must not have more than one active admission.

**BR-03 — Valid Ward Types:** The database shall accept only Intensive Care, General Medicine, Surgery, and Emergency as WardType values in the current MVP.

**BR-04 — Alert Priority:** The system shall accept only LOW, HIGH, and CRITICAL alert priorities.

**BR-05 — Alert Escalation:** Only unacknowledged HIGH and CRITICAL alerts qualify for automatic escalation after 30 seconds.

**BR-06 — Nurse Availability:** Escalation recipients must have Available status.

**BR-07 — Access Control:** Users shall access only information and operations permitted by their assigned roles.

**BR-08 — Alert Logging:** The system shall record alert creation, assignment, acknowledgement, and escalation with timestamps.

**BR-09 — Authentication:** A badge shall be locked for five minutes after five incorrect PIN attempts.

**BR-10 — Session Duration:** Authenticated sessions shall have a maximum configured lifetime of 12 hours.

## 6. Glossary

| Term | Definition |
|---|---|
| MVP | Minimum Viable Product: the smallest agreed version of the system. |
| UC | Use Case: a specific user interaction or system process. |
| FR | Functional Requirement: a behavior the system must perform. |
| NFR | Non-Functional Requirement: a measurable quality or operational constraint. |
| Ward | A hospital unit containing patient beds. |
| Admission | A record of a patient's placement in a ward. |
| Ward Capacity | The maximum number of patients a ward can accommodate. |
| Active Admission | An admission that has not been discharged. |
| Alert | A notification generated by the patient-monitor or call-button simulator. |
| Alert Priority | The urgency classification LOW, HIGH, or CRITICAL. |
| Acknowledgement | Confirmation by a nurse that an alert has been received and accepted. |
| Escalation | Forwarding an unacknowledged alert to another available nurse. |
| Available | A nurse status indicating eligibility to receive escalated alerts. |
| Busy | A nurse status indicating that the nurse is unavailable for escalation. |
| OffShift | A nurse status indicating that the nurse is not currently on duty. |
| Badge ID | A unique staff identifier used during login. |
| PIN | A numeric authentication secret used with the badge ID. |
| RBAC | Role-Based Access Control: permissions determined by user roles. |
| Audit Log | A record of important system events and their timestamps. |
| Response Time | The time between alert creation and acknowledgement. |
| Database Transaction | A group of operations that succeeds together or is rolled back. |
| CI | Continuous Integration: automated checks performed on code changes. |
