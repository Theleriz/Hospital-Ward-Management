# Архитектура и безопасность Hospital Ward Management System

**Задача:** T-30

**Ответственный:** Shynbulat Kazbek (24B032123), Architecture & Security

**Статус документа:** соответствует коду после T-27 (11 ноября 2026 года); будущие компоненты явно помечены как планируемые

Документ описывает компоненты системы, движение данных, контракт API, роли,
границы доверия и модель угроз. Принятые решения зафиксированы в
[`decisions.md`](decisions.md), а границы MVP и сценарии UC-1 — UC-8 — в
[`project-plan.md`](project-plan.md).

## 1. Назначение и границы

Система предназначена для одного отделения больницы и поддерживает два
процесса:

1. **Коечный фонд:** регистрация пациента, госпитализация, перевод, выписка и
   просмотр занятости палат.
2. **Оповещения медсёстрам:** создание оповещения симулятором устройства,
   назначение и подтверждение, эскалация HIGH/CRITICAL через 30 секунд и отчёт
   о времени реакции.

MVP работает во внутренней сети. Реальные медицинские устройства,
RFID-инфраструктура, мобильное приложение, медицинская карта, несколько
отделений, доступ из интернета и интеграции HL7/FHIR в него не входят.

## 2. Архитектурные принципы

- Вся система запускается одной командой `docker compose up -d --build --wait`.
- Браузер обращается к одному адресу; nginx отдаёт React-приложение и передаёт
  `/api` в FastAPI.
- Backend — основной слой бизнес-логики и контроля доступа.
- PostgreSQL независимо повторяет критичные проверки ограничениями,
  процедурами и правами ролей.
- Критичные изменения данных выполняются через хранимые процедуры.
- Пользователь получает только минимально необходимые данные своей роли.
- Журнал событий оповещений является добавочным: существующие события нельзя
  изменять или удалять через роли приложения.
- Незавершённые компоненты и API не выдаются за реализованные.

## 4. Развёртывание и границы доверия

Docker Compose поднимает три контейнера:

- `medbase-frontend`: nginx, опубликован на `127.0.0.1:8080`;
- `medbase-backend`: FastAPI, опубликован на `127.0.0.1:8000` для разработки;
- `medbase-postgres`: PostgreSQL, опубликован на `127.0.0.1:55440` для
  разработки.

Публикация только на loopback не делает production-развёртывание безопасным
сама по себе. При установке в отделении внешний вход должен идти через HTTPS,
а порт PostgreSQL не должен быть доступен рабочим станциям.

Границы доверия:

1. **Браузер → nginx/FastAPI.** Ввод пользователя и cookie считаются
   недоверенными; backend проверяет формат, сессию и роль.
2. **FastAPI → PostgreSQL.** Ошибка или обход проверки backend не должны давать
   лишних прав: запрос выполняется под ролью пользователя в БД.
3. **Симулятор/worker → FastAPI или БД.** Создание и эскалация оповещений
   разрешаются только сервисной роли; пользовательский интерфейс не должен
   получать эти права.
4. **Репозиторий/CI → развёртывание.** В `main` попадают только изменения через
   PR и зелёную обязательную проверку.

## 5. Данные и правила целостности

Основные сущности:

| Сущность | Назначение | Ключевые правила |
|---|---|---|
| `Patient` | Пациенты | Уникальный телефон, обязательная дата рождения |
| `Ward` | Палаты | Вместимость больше нуля, допустимый тип палаты |
| `Admission` | История госпитализаций | Один активный приём пациента; дата выписки не раньше госпитализации |
| `Nurse` | Медсёстры | Уникальный бейдж, bcrypt-хэш PIN, допустимый статус |
| `NurseAssignment` | Назначение на палату | Одна основная медсестра на палату |
| `StaffAccount` | Другие сотрудники | Уникальный бейдж, bcrypt-хэш PIN, роль и активность |
| `WardAlert` | Текущее состояние оповещения | Назначенная, эскалированная и подтвердившая медсестра хранятся отдельно |
| `AlertEvent` | История жизненного цикла оповещения | Только добавление событий; UPDATE/DELETE блокируются |

Критичные операции выполняют процедуры:

- `sp_RegisterAndAdmitPatient`, `sp_AdmitPatient`, `sp_DischargePatient`;
- `sp_RaiseAlert`, `sp_EscalateAlert`, `sp_AcknowledgeAlert`;
- `sp_SetNurseStatus`;
- `fn_AuthenticateStaff` проверяет бейдж и PIN внутри базы.

Вместимость палаты и одновременная госпитализация защищены не только
предварительным чтением, но и блокировками/ограничениями внутри транзакции.

## 6. Основные потоки данных

### 6.1. Вход пользователя — реализовано

1. Пользователь вводит ID бейджа и PIN в браузере.
2. React отправляет `POST /api/auth/login` по тому же origin.
3. FastAPI проверяет формат и локальную блокировку попыток входа.
4. Backend вызывает `fn_AuthenticateStaff`; сравнение с bcrypt-хэшем происходит
   внутри PostgreSQL, хэш не возвращается приложению.
5. При успехе FastAPI создаёт подписанную `HttpOnly` cookie на 12 часов.
6. Неизвестный бейдж, неверный PIN и неактивная учётная запись возвращают один
   ответ, поэтому по сообщению нельзя определить существование бейджа.

### 6.2. Авторизованный запрос — реализовано

1. Браузер автоматически отправляет session cookie.
2. FastAPI проверяет подпись и извлекает пользователя и роль.
3. Endpoint проверяет разрешённые роли через `require_roles` (или `role_db`, которая
   проверяет роль и сразу выдаёт соединение под ролью пользователя).
4. Backend берёт соединение пула как `medbase_api`.
5. Внутри транзакции выполняется `SET LOCAL ROLE` для роли пользователя.
6. PostgreSQL повторно проверяет право на таблицу, представление или процедуру.
7. После commit/rollback локальная роль сбрасывается до возврата соединения в
   пул.

### 6.3. Госпитализация, перевод и выписка — реализовано (T-22)

1. Приёмное отделение отправляет данные пациента и палаты
   (`POST /api/admissions`) или выбирает перевод и выписку в списке пациентов.
2. Backend проверяет роль `Admissions` (`role_db`) и формат полей
   (Pydantic: ФИО, дата рождения не в будущем, телефон, пол, палата).
3. Backend проверяет бизнес-правила и отвечает понятным сообщением: палата
   существует и в ней есть свободное место; пациент с этим телефоном ещё не лежит
   в отделении (иначе backend просит оформить перевод, а не переводит молча);
   перевод идёт не в ту же палату; выписывается пациент, который лежит в
   отделении.
4. Процедура БД (`sp_RegisterAndAdmitPatient`, `sp_AdmitPatient`,
   `sp_DischargePatient`) повторно проверяет пациента, палату, вместимость и
   активную госпитализацию в одной транзакции с блокировками строк.
5. Если процедура всё же отказывает (например, параллельный запрос занял
   последнее место), API отвечает `409` с текстом сообщения процедуры
   (`app/db_errors.py`). SQL, stack trace и реквизиты подключения клиенту не
   передаются.
6. Табло палат (`GET /api/wards`, T-23) читает `vw_WardCapacity` под ролью
   пользователя и не содержит данных пациентов.

### 6.4. Оповещение, подтверждение и эскалация — реализовано (T-24 — T-26)

1. Симулятор (`POST /api/simulator/alerts`, доступен медсёстрам, только для
   демо) действует как `medbase_alert_service`. Backend проверяет палату и что
   пациент лежит в ней, выбирает медсестру палаты на смене (основную, затем
   другую, свободную раньше занятой) и вызывает `sp_RaiseAlert`; процедура
   повторно проверяет выбор.
2. Пост медсестры опрашивает `GET /api/alerts` раз в секунду: это укладывается
   в NFR-01 (2 секунды) и проще потока событий. Медсестра видит оповещения своих
   палат и назначенные или эскалированные на неё; старшая медсестра видит все.
   Новые HIGH и CRITICAL сопровождаются звуком.
3. Подтверждение (`POST /api/alerts/{id}/acknowledge`): backend проверяет, что
   оповещение ещё не подтверждено, медсестра на смене и оповещение её; затем
   `sp_AcknowledgeAlert` проверяет то же самое ещё раз.
4. Фоновый поток backend каждые ~2 секунды под ролью `medbase_alert_service`
   ищет PENDING HIGH/CRITICAL старше 30 секунд и выбирает медсестру со статусом
   `Available`, кроме назначенной, сначала из той же палаты. `sp_EscalateAlert`
   повторно проверяет 30 секунд, приоритет, статус и доступность медсестры,
   поэтому параллельное подтверждение или повторный проход не дают двойной
   эскалации. Если свободных медсестёр нет, оповещение ждёт следующего прохода.
5. Триггер записывает переходы состояния в `AlertEvent`.

### 6.5. Отчёт старшей медсестры — реализовано (T-27)

1. Экран «Отчёт старшей медсестры» доступен только `HeadNurse` и обновляется
   раз в 30 секунд. Период выбирается: смена (12 ч), сутки, 7 или 30 дней.
2. `GET /api/reports/alerts?hours=N` выполняется под ролью
   `medbase_head_nurse` и читает представление `vw_AlertResponse`: сводку
   (всего, подтверждено, открыто, эскалировано, среднее, медиана и максимум
   времени реакции, доля подтверждённых за 30 с), разрез по приоритетам, разрез
   по медсёстрам и историю оповещений (последние 500).
3. Время реакции = `AcknowledgedAt − CreatedAt` (FR-29) и считается в
   представлении, поэтому совпадает в SQL-отчёте и в API.
4. `GET /api/reports/alerts/{alert_id}/events` показывает журнал одного
   оповещения из `AlertEvent`: создание, назначение, эскалацию, подтверждение.
5. Отчёт только читает данные и не содержит данных пациента.

## 7. Контракт API

### 7.1. Реализованные endpoints

| Метод и путь | Доступ | Назначение | Основные ответы |
|---|---|---|---|
| `GET /api/health` | Без входа | Состояние backend и БД | `200`, `503` |
| `POST /api/auth/login` | Без входа | Вход по бейджу и PIN | `200`, `401`, `422`, `429` |
| `POST /api/auth/logout` | Сессия необязательна | Завершение сессии | `204` |
| `GET /api/auth/me` | Любая активная роль | Текущий пользователь | `200`, `401` |
| `GET /api/docs` | Без входа в dev-среде | Swagger UI | `200` |
| `GET /api/wards` | Любая активная роль | Занятость палат без данных пациентов | `200`, `401` |
| `GET /api/admissions/active` | `Admissions` | Пациенты, которые сейчас лежат в отделении | `200`, `401`, `403` |
| `POST /api/admissions` | `Admissions` | Регистрация (или поиск по телефону) и госпитализация | `201`, `401`, `403`, `404`, `409`, `422` |
| `POST /api/admissions/{patient_id}/transfer` | `Admissions` | Перевод в другую палату | `200`, `401`, `403`, `404`, `409`, `422` |
| `POST /api/admissions/{patient_id}/discharge` | `Admissions` | Выписка | `204`, `401`, `403`, `404`, `409` |
| `GET /api/alerts` | `Nurse`, `HeadNurse` | Активные оповещения и подтверждённые за час | `200`, `401`, `403` |
| `POST /api/alerts/{alert_id}/acknowledge` | `Nurse`, `HeadNurse` | Подтверждение оповещения | `200`, `401`, `403`, `404`, `409` |
| `GET /api/nurses/me` | `Nurse`, `HeadNurse` | Свой статус и палаты | `200`, `401`, `403` |
| `PUT /api/nurses/me/status` | `Nurse`, `HeadNurse` | Смена своего статуса | `200`, `401`, `403`, `422` |
| `GET /api/simulator/wards` | `Nurse`, `HeadNurse`; только при включённом симуляторе | Палаты, пациенты и медсестра на смене | `200`, `401`, `403`, `404` |
| `POST /api/simulator/alerts` | `Nurse`, `HeadNurse`; только при включённом симуляторе | Оповещение от имени устройства | `201`, `401`, `403`, `404`, `409`, `422` |
| `GET /api/reports/alerts?hours=N` | `HeadNurse` | Отчёт за последние N часов (1–720, по умолчанию 24): сводка, приоритеты, медсёстры, история | `200`, `401`, `403`, `422` |
| `GET /api/reports/alerts/{alert_id}/events` | `HeadNurse` | Журнал одного оповещения | `200`, `401`, `403`, `404`, `422` |

Поля ответа пользователя: `account_id`, `full_name`, `role`. PIN, PIN-хэш,
пароль БД и содержимое session cookie API не возвращает. Ответ табло палат:
`ward_id`, `ward_name`, `floor`, `ward_type`, `capacity`, `occupied`,
`available` — без данных пациентов.

### 7.2. Общие правила

Общие правила контракта:

- JSON используется для запросов и ответов; пост медсестры получает обновления опросом раз в секунду.
- `401` означает отсутствие/недействительность сессии, `403` — недостаточную
  роль, `404` — отсутствие объекта, `409` — конфликт бизнес-правила, `422` —
  неверный формат входа, `429` — временное ограничение частоты.
- Клиенту возвращается безопасное сообщение; SQL, stack trace и реквизиты
  подключения остаются в серверном журнале.
- Каждый новый endpoint получает тесты на разрешённые и запрещённые роли.

## 8. Роли и доступ

| Роль приложения | Роль PostgreSQL | Разрешённые действия |
|---|---|---|
| `Admissions` | `medbase_admissions` | Пациенты, госпитализация, перевод, выписка, занятость палат |
| `PublicStaff` | `medbase_public_staff` | Только `vw_WardCapacity`, без персональных данных |
| `Nurse` | `medbase_nurse` | Оповещения, ограниченные данные пациента, подтверждение, собственный статус |
| `HeadNurse` | `medbase_head_nurse` (входит в `medbase_nurse`) | Возможности медсестры, отчёт `vw_AlertResponse` и журнал `AlertEvent` |
| Сервис оповещений | `medbase_alert_service` | Создание и эскалация оповещений, минимально нужное чтение (имена пациентов для симулятора, без телефонов) |
| Backend login | `medbase_api` | Сам данных не читает; может переключаться в разрешённые роли |

`medbase_api` создан с `NOINHERIT`. Он подключается к БД, но без `SET LOCAL
ROLE` не имеет доступа к бизнес-данным. Прямой INSERT/UPDATE в `WardAlert` и
`AlertEvent` ролям приложения не выдаётся.

`HeadNurse` получает отдельную роль БД `medbase_head_nurse` ([decisions.md](decisions.md),
запись 8). Отчёт и журнал оповещений закрыты для `medbase_nurse` на уровне БД, а
backend отвечает `403` всем ролям, кроме `HeadNurse`.

## 9. Защита сессии и учётных данных

- PIN хранится только как bcrypt-хэш и сравнивается внутри БД.
- PIN принимается только в формате 4–8 цифр.
- После пяти неудачных попыток бейдж блокируется на пять минут.
- Ответ при неверных данных одинаковый, чтобы не раскрывать существование
  учётной записи.
- Cookie подписана, имеет `HttpOnly`, `SameSite=Lax` и срок 12 часов.
- В HTTPS-развёртывании обязательно включается
  `MEDBASE_SESSION_HTTPS_ONLY=true`, добавляющий флаг `Secure`.
- Секрет сессии и пароль `medbase_api` из `docker-compose.yml` являются только
  значениями для локальной разработки и должны заменяться секретами окружения.
- Приложение не должно записывать PIN, cookie или строки подключения в логи.

## 10. Модель угроз

Рассматриваются недоверенный пользователь внутренней сети, сотрудник с
ограниченной ролью, атакующий с доступом к браузеру/трафику, ошибка backend и
ошибка конфигурации развёртывания.

| Угроза | Возможный ущерб | Текущая защита | Остаточный риск / действие |
|---|---|---|---|
| Подбор короткого PIN | Несанкционированный вход | Пять попыток, блокировка на 5 минут, bcrypt | Счётчик хранится в памяти и сбрасывается при рестарте; для нескольких backend-инстансов перенести в БД/Redis |
| Определение существующего бейджа | Подготовка целевой атаки | Одинаковый `401` для неизвестного бейджа и неверного PIN | Ограничивать частоту также по IP/устройству в production |
| Подделка session cookie | Захват роли пользователя | Подпись cookie; тест изменения cookie | Использовать длинный случайный секрет и ротацию |
| Перехват cookie по сети | Захват сессии | `HttpOnly`, опциональный `Secure` | Локальный HTTP небезопасен для production; обязателен HTTPS и `Secure` |
| CSRF для изменяющего запроса | Действие от имени вошедшего пользователя | `SameSite=Lax`, JSON API, один origin | Перед внешним доступом добавить проверку Origin/CSRF-токен и тесты |
| Обход проверки роли в endpoint | Чтение/изменение чужих данных | `require_roles` и независимые права PostgreSQL | Для каждого нового endpoint нужны позитивные и негативные role-тесты |
| SQL injection | Чтение или изменение БД | Параметры psycopg; безопасный `Identifier` для ролей; процедуры | Не собирать SQL конкатенацией; проверять новые запросы на code review |
| Лишние права backend | Компрометация всех данных при ошибке | `medbase_api NOINHERIT`, `SET LOCAL ROLE`, минимальные GRANT | `medbase_api` может переключаться в сервисные роли; выбор роли никогда не должен поступать от клиента |
| Чтение PIN-хэшей | Офлайн-подбор PIN | Нет SELECT на столбец хэша; проверка внутри функции БД | Владелец/администратор БД остаётся доверенным субъектом |
| Изменение журнала событий | Сокрытие задержки или ошибки | Append-only trigger и отсутствие UPDATE/DELETE у ролей | Защитить административные учётные записи и резервные копии |
| Переполнение палаты при гонке | Некорректная госпитализация | Предварительная проверка в backend, затем транзакция, блокировки и повторная проверка процедуры; отказ процедуры — `409` | Сохранять конкурентный ручной тест при изменении процедуры |
| Поддельное оповещение | Ложная тревога | Создание только сервисной процедурой/ролью; симулятор доступен лишь медсёстрам и выключается `MEDBASE_SIMULATOR_ENABLED=false` | Выключать симулятор вне demo-среды; аутентифицировать устройство при реальной интеграции |
| Поток ложных запросов/оповещений | Отказ в обслуживании | Ограниченная внутренняя сеть | Добавить rate limit, лимиты тела запроса и мониторинг перед production |
| Утечка dev-секретов | Доступ к БД или подделка сессии | README явно помечает значения как dev-only | Удалить значения по умолчанию для production, использовать secret manager |
| Сломанный или вредоносный dependency | Выполнение стороннего кода | Зафиксированные версии зависимостей | Добавить автоматическое сканирование зависимостей и обновления через PR |
| Потеря данных | Недоступность истории и аудита | Данные в Docker volume | T-44: `pg_dump`, проверка восстановления и хранение копии вне хоста |

## 11. Требования к новым endpoint и экранам

Перед включением новой функции в `main` необходимо проверить:

- роль разрешена явно, а остальные роли получают `403`;
- запрос к БД выполняется через `user_db`/`role_db` или контролируемую сервисную роль;
- имя роли или SQL-выражение не берётся напрямую из запроса клиента;
- критичная запись выполняется процедурой БД;
- ответ не содержит лишних персональных данных, PIN-хэшей и внутренних ошибок;
- вход валидируется Pydantic-моделью с ограничениями длины/диапазона;
- есть успешный тест, тест неверного ввода, `401` и `403`;
- изменение поведения отражено в Swagger, демо и документации;
- экран с опросом переживает временную недоступность сервера и показывает это;
- для фоновой задачи повторный запуск безопасен и не создаёт двойную
  эскалацию.

## 13. Известные ограничения

- `MEDBASE_SESSION_SECRET` и пароль `medbase_api` в Compose предназначены только
  для разработки.
- В локальном запуске используется HTTP; production-профиль с TLS пока не
  подготовлен.
- Ограничение попыток входа хранится в памяти одного backend-процесса.
- История в отчёте старшей медсестры ограничена последними 500 оповещениями периода; сводка считает все.
- Фоновая эскалация рассчитана на один экземпляр backend; при нескольких
  экземплярах двойную эскалацию не допустит процедура, но проходы будут дублироваться.
- CI пока обязательно проверяет только базу данных.
- Централизованный мониторинг, ротация секретов и проверенное восстановление из
  бэкапа находятся за пределами текущего состояния.
