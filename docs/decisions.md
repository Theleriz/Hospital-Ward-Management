Issue: Границы MVP: что входит в систему  
Description: У проекта не было зафиксированного результата, к которому мы идём, поэтому нельзя было делить работу на этапы и задачи.  
Decision: MVP — система одного отделения больницы с двумя процессами: коечный фонд и оповещения медсёстрам. Входят сценарии: UC-1 регистрация и госпитализация; UC-2 перевод в другую палату; UC-3 выписка; UC-4 занятость палат без данных пациентов; UC-5 поступление оповещения и показ на посту; UC-6 вход медсестры по бейджу или PIN и подтверждение оповещения; UC-7 эскалация через 30 секунд; UC-8 отчёт старшей медсестры по времени реакции и эскалациям. Результат к защите: одна команда `docker compose up` поднимает всю систему, и полный сценарий проходится в браузере.  
Reference: docs/project-plan.md, разделы 2 и 3; запись 1.

Расширить границы можно только новой записью в этом журнале.

Issue: Стек: backend на FastAPI  
Description: Для этапа «Backend и интерфейс» нужно выбрать backend. Рассматривались FastAPI (Python) и Java (Spring Boot); интерфейс на React и база PostgreSQL уже определены.  
Decision: Backend — Python 3.12 + FastAPI + psycopg 3. Интерфейс — React. База данных — PostgreSQL. Тесты backend пишутся на pytest. Причины: меньше кода на каждый сценарий, Swagger-страница API генерируется автоматически (по ней можно проверять API без кода и показывать его на защите), тесты на pytest проще писать участникам, которые мало программируют, поток событий в реальном времени (SSE) поддерживается без дополнительных библиотек. Стек можно усложнять в будущем, каждый раз новой записью.

Issue: Два независимых слоя защиты: backend и процедуры БД  
Description: Ошибка в backend (пропущенная проверка, неверный запрос) не должна приводить к некорректным данным: пациент в заполненной палате, подтверждение чужого оповещения, эскалация на занятую медсестру. Нужно решить, где живут бизнес-логика и проверки.  
Decision: (1) Бизнес-логика, проверки и защита (вход, роли, права доступа) реализуются в backend — это основной слой. (2) База данных — второй слой, подстраховка: критичные операции проходят через процедуры БД, которые вместе с ограничениями (CHECK, внешние ключи, уникальные индексы) и правами ролей повторно проверяют правила и не дают записать некорректные данные, даже если backend ошибся. (3) Слои не зависят друг от друга: backend не полагается на проверки БД, а БД не полагается на проверки backend. Каждый слой покрыт своими тестами: SQL-тесты проверяют БД без backend, тесты backend — его логику. (4) За бизнес-логику и управление БД отвечают Rishat Zhanat и Zhanserikuly Nurali.  
Reference: запись 4; docs/project-plan.md, разделы 3, 4 и 6.

Issue: Инструменты интерфейса и запуск в Docker  
Description: Запись 4 определила React, но не то, на чём собирается интерфейс и как backend и интерфейс запускаются вместе с базой одной командой (NFR-05).  
Decision: (1) Интерфейс — React + TypeScript, сборка Vite. TypeScript выбран, чтобы типы ответов API проверялись при сборке. (2) В Docker интерфейс собирается и отдаётся через nginx, который проксирует `/api` в backend; так браузер работает с одним адресом и без настроек CORS. (3) `docker compose up` поднимает три сервиса: `db`, `backend`, `frontend`; backend стартует после готовности базы, интерфейс — после готовности backend. (4) Версии зависимостей фиксируются точно (`requirements.txt`, `package-lock.json`).  
Reference: запись 4; docs/project-plan.md, задача T-20.

Issue: Вход по бейджу и PIN, сессии и права в двух слоях  
Description: Нужно решить, как сотрудники входят в систему (Lab 5: бейдж, запасной вариант — PIN), где хранится сессия и как права пользователя проверяются не только в backend, но и в базе (запись 5).  
Decision: (1) Вход — номер бейджа и PIN из 4–8 цифр. PIN сверяется с bcrypt-хэшем внутри базы функцией `fn_AuthenticateStaff`, поэтому хэши PIN не читает ни одна роль приложения. Неизвестный бейдж и неверный PIN дают одинаковый ответ. (2) После 5 неверных PIN бейдж блокируется на 5 минут. (3) Сессия — подписанная httponly cookie (SameSite=Lax) на 12 часов, одну смену; за HTTPS включается флаг Secure (`MEDBASE_SESSION_HTTPS_ONLY`). (4) Права пользователя проверяет backend (основной слой). Кроме того, backend подключается к базе ролью `medbase_api`, которая сама по себе не видит данных, и на каждый запрос переключается (`SET LOCAL ROLE`) в роль пользователя: `medbase_admissions`, `medbase_public_staff` или `medbase_nurse`. Так база проверяет права ещё раз. (5) Сотрудники, которые не медсёстры, хранятся в `StaffAccount`; один бейдж принадлежит ровно одному человеку.  
Reference: записи 5 и 6; docs/works/Zhanat_Rishat/24B031775_Zhanat_Rishat_Task5.docx (вход по бейджу, Plan B — PIN); docs/project-plan.md, задача T-21.
