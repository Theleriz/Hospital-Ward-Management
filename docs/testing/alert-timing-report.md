Автор: Shynbulat Kazbek (Kazbekio), Architecture & Security, 18 ноября 2026.

## Запуск и результат

Из корня этой ветки, нужен Docker с Compose:

```bash
bash scripts/check-alert-timing.sh
```

Первый запуск загружает Chromium и зависимости; дальнейшие используют кэш
сборки. Затем запускаются настоящие React/nginx, FastAPI с включённым worker
и чистый PostgreSQL. Измерения занимают около четырёх минут. Не вводить другие
команды в этот же терминал до возврата приглашения оболочки.

Проверка использует отдельную сеть/базу, без опубликованных портов, фиксированных
имён контейнеров и рабочего volume приложения. После завершения окружение
удаляется. Настройки приложения остаются штатными: опрос 1 с, worker 2 с,
эскалация 30 с. Ни часы, ни CreatedAt/EscalatedAt не ускоряются и не меняются.

Результаты в `artifacts/alert-timing/`:

- `results.json` — версия кода, Python/Chromium/Playwright, все измерения и статус;
- `measurements.csv` — таблица для итогового отчёта Baigel (T-42);
- `report.md` — читаемый отчёт с минимумом, медианой и максимумом;
- `services.log` и browser trace; при ошибке — снимки экранов.

Трассировки содержат только синтетические учётные записи/данные этой отдельной
БД. В репозиторий они не коммитятся. Несоответствие требованиям возвращает
ненулевой код, даже если сервисы успешно запустились.

### Границы измерения

Симулятор и посты открыты в независимых браузерных сессиях. Сигнал создаётся
кнопкой симулятора, а не прямым SQL. Скрипт запоминает `perf_counter` при
событии отправки POST и тем же таймером — подтверждение видимости карточки
с полученным AlertID. Это **верхняя оценка** доставки от создания: она включает
обработку POST, commit, ожидание опроса, GET и отрисовку. Часы браузера и БД
друг из друга не вычитаются, длительность ответа API не выдаётся за время UI.

12 измерений: LOW/HIGH/CRITICAL × четыре смещения (0/250/500/750 мс) после
реального опроса поста. Каждое должно быть ≤2 с. После измерения сигнал
подтверждается, чтобы не запускать лишние эскалации. Headless Chromium
запускается без фонового замедления вкладок: проверяется активный пост,
а не вкладка, которую браузер приостановил. Это обычная работа одного отделения,
не нагрузочный тест и не доказательство для любой сети/машины.

## Методика NFR-02 и отрицательные проверки

Для HIGH и CRITICAL скрипт ждёт первую и повторную эскалацию по настоящим
30 секундам. Разности берутся из `AlertEvent`: CREATED → первая ESCALATED,
затем первая → вторая ESCALATED. Каждая должна быть 30–35 с. Проверяется
и появление карточки у реального получателя: сначала NURSE-04 своего этажа,
затем NURSE-03 другого этажа. После второй эскалации сигнал подтверждается.

LOW и заранее подтверждённый HIGH наблюдаются более 60 с и не должны иметь
ESCALATED в журнале. Busy/OffShift не становятся получателями. При отсутствии
других Available новый HIGH остаётся PENDING после 36 с: это ожидаемое
ограничение, **не успешное выполнение доставки за 35 с**.

SQL владельца используется только в одноразовом окружении для удаления
исходных демонстрационных сигналов, задания доступности медсестёр и чтения
журнала. `sp_EscalateAlert` напрямую скрипт не вызывает.
