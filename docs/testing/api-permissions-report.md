## 2. Ожидаемые права, заданные независимо от реализации

`401` — нет действительной сессии; `403` — вошёл, но право не предоставлено;
`200/201/204` — операция разрешена. Матрица задаёт ожидаемое поведение явно,
не копирует роли из зависимостей проверяемого endpoint.

| Метод и endpoint | Без входа | Admissions | PublicStaff | Nurse | HeadNurse |
|---|---|---|---|---|---|
| GET `/api/auth/me` | 401 | 200 | 200 | 200 | 200 |
| GET `/api/wards` | 401 | 200 | 200 | 200 | 200 |
| GET `/api/admissions/active` | 401 | 200 | 403 | 403 | 403 |
| POST `/api/admissions` | 401 | 201 | 403 | 403 | 403 |
| POST `/api/admissions/3/transfer` | 401 | 200 | 403 | 403 | 403 |
| POST `/api/admissions/3/discharge` | 401 | 204 | 403 | 403 | 403 |
| GET `/api/alerts` | 401 | 403 | 403 | 200 | 200 |
| POST `/api/alerts/ALT-1001/acknowledge` | 401 | 403 | 403 | 200 | 403* |
| GET `/api/nurses/me` | 401 | 403 | 403 | 200 | 200 |
| PUT `/api/nurses/me/status` | 401 | 403 | 403 | 200 | 200 |
| GET `/api/reports/alerts` | 401 | 403 | 403 | 403 | 200 |
| GET `/api/reports/alerts/ALT-1006/events` | 401 | 403 | 403 | 403 | 200 |
| GET `/api/simulator/wards` | 401 | 403 | 403 | 200 | 200 |
| POST `/api/simulator/alerts` | 401 | 403 | 403 | 201 | 201 |

**70 комбинаций** = 14 действий × 5 состояний пользователя. Симулятор включён.
Запросы используют корректные тела и существующие объекты seed, поэтому
отказ не маскируется ошибкой валидации или отсутствием объекта.

\* В seed `NURSE-10` — старшая медсестра без назначенной палаты. Она может
смотреть все оповещения, но не может подтвердить `ALT-1001`: для этого нужны
назначение, эскалация на неё либо работа в палате 101. Это проверка права на
конкретный объект поверх права роли на endpoint. Обычная `NURSE-01` работает
в палате 101 и получает `200`.

## 3. Дополнительные security-проверки

| Проверка | Что подтверждает | Количество |
|---|---|---|
| Запрет роли до открытия соединения | PublicStaff получает 403 даже если доступ к пулу БД намеренно запрещён тестом | 1 |
| Попытка передать чужую роль | `?role=Admissions`, X-Role и X-Account-ID не повышают PublicStaff | 1 |
| Точный состав ответа табло | Только 7 полей палаты, нет имени/телефона пациента | 1 |
| Подтверждение из чужой палаты | Nurse-04 получает 403 для сигнала палаты 101; данные не меняются | 1 |
| Перебор ID пациента | Nurse получает одинаковый 403 для существующего и неизвестного patient_id | 1 |
| Выключенный симулятор | Даже HeadNurse получает 404, создание данных исключено | 1 |
| Прямой SQL под ограниченной ролью | Запрет персональных данных, PIN-хэшей, госпитализации медсестрой, прямой записи сигнала и удаления журнала; отчёт `vw_AlertResponse` и журнал `AlertEvent` закрыты для медсестры и приёмного отделения | 11 |
| Переиспользование одного соединения | После COMMIT и ROLLBACK роль сбрасывается; PublicStaff не получает права Admissions | 2 |

Итого: **89 тестовых случаев**. Все 401/403 матрицы и отрицательные SQL-тесты
сравнивают содержимое восьми бизнес-таблиц до и после запроса, а не только
количество строк. Это обнаруживает также незаметное изменение существующей
строки. Снимки выполняются владельцем только из теста; сам API использует
`medbase_api` и ограниченные роли.

## 4. Как воспроизвести в VS Code

Из корня проекта, с запущенным Docker:

```bash
bash scripts/check-api-permissions.sh
```

Нужны Docker Compose и доступ к реестру образов/PyPI при первом запуске.
Скрипт создаёт отдельный Docker project с уникальным именем, без опубликованных
портов, без `medbase-postgres` и без рабочего volume приложения. После запуска
он удаляет только свой тестовый project и его volumes. Тесты перезаливают seed
перед каждым случаем; запускать их на рабочей БД с реальными данными нельзя.

Результат в терминале: имена проверок и итог pytest. Машиночитаемое
доказательство: `artifacts/api-permissions/junit.xml`, в матричных случаях
также записаны метод/путь, роль, ожидаемый и фактический HTTP-статус.
Артефакты не коммитятся. Для машины с уже собранным backend-образом:

```bash
MEDBASE_PERMISSIONS_TEST_IMAGE=hospital-ward-management-backend:latest bash scripts/check-api-permissions.sh
```

При локальном Python-окружении для разработки (только отдельная тестовая БД):

```bash
cd backend
python -m pytest tests/test_api_permissions.py -v
```

## 6. Что показывает эта работа и что ещё нужно проверить

Проверки дают воспроизводимое доказательство разделения ролей для выбранного
среза исходников. Они не являются полным аудитом безопасности. Здесь нет
измерения доставки сигнала в браузер за 2 секунды, проверки физического
считывателя, TLS, CSRF, нагрузки или production-конфигурации.

Отдельно остаются известные ограничения текущей модели: возможность
технической `medbase_api` переключаться в несколько ролей; блокировка PIN в
памяти; административный доступ к БД. Общей роли Nurse и HeadNurse больше нет:
старшая медсестра работает под `medbase_head_nurse` (решение 8).
Разделение PostgreSQL-ролей защищает от запроса под корректной ограниченной
ролью, но не от полного захвата backend или выбора им привилегированной роли.

Endpoints отчёта `/api/reports/...` и роль `medbase_head_nurse` добавлены в
матрицу: доступ есть только у HeadNurse, остальные получают 401/403. Обязательные backend-проверки CI согласуются с Lead в рамках T-28; правила
ветки и существующий DB CI в этой работе не меняются.
