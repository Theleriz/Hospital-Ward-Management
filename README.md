# Hospital Ward Management — Team MedBase

Информационная система одного отделения больницы. Она закрывает два процесса:

- **коечный фонд** — регистрация, госпитализация, перевод и выписка пациентов, табло занятости палат (Task 09);
- **оповещения медсёстрам** — сигнал от монитора или кнопки вызова появляется на посту медсестры, неподтверждённый HIGH/CRITICAL через 30 секунд эскалируется, старшая медсестра видит время реакции (Lab 04 / Task 07).

Состав: PostgreSQL 17, backend на FastAPI, интерфейс на React. Вся система поднимается одной командой `docker compose up`. План, этапы и задачи — в [docs/project-plan.md](docs/project-plan.md).

## Правила работы с репозиторием

Подробно с командами: [CONTRIBUTING.md](CONTRIBUTING.md).

1. **Ветка `main` всегда готова к демо.** В любой момент из `main` можно показать корректно работающий проект: база собирается с нуля, автотесты проходят, `db/demo.sql` отрабатывает до конца. Всё это проверяет одна команда `bash scripts/check-db.sh`, и та же проверка автоматически запускается в CI на каждый PR. Незаконченная работа в `main` не попадает.
2. **Все изменения — через Pull Request (PR).** Прямой push в `main` запрещён, PR сливается только при зелёных проверках CI (`db-check`, `backend-tests`, `frontend-build`, `system-start`) и ветке, актуальной относительно `main`; это закреплено правилами ветки на GitHub. Сливают PR в `main` Rishat (`theleriz`) и Baigel (`Ba1igel`), остальные участники открывают PR и ждут слияния. Пушить в `main` напрямую может только `theleriz` как админ репозитория.
3. **Начинать работу от свежей `main`.** Перед новой функциональностью или новым документом обновите `main` и создайте ветку от неё, чтобы не было рассинхрона:

   ```bash
   git checkout main
   git pull origin main
   git checkout -b feature/<название>
   ```

## Запуск

Вся система (база, backend, интерфейс) поднимается одной командой:

```bash
docker compose up -d --build --wait
```

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:8080 |
| API | http://localhost:8080/api/… (через nginx) или http://localhost:8000/api/… (напрямую) |
| Документация API (Swagger) | http://localhost:8080/api/docs |
| Проверка состояния | http://localhost:8080/api/health |

`--build` пересобирает backend и интерфейс после изменений в коде. Только база: `docker compose up -d --wait db`.

### Вход

Вход по бейджу и PIN. Считыватель бейджей работает как клавиатура: вводит номер и нажимает Enter, после чего курсор переходит в поле PIN. Без считывателя номер бейджа вводится вручную. Тестовые учётные записи (только для разработки, полный список — в начале [db/04_seed.sql](db/04_seed.sql)):

| Роль | Бейдж | PIN |
|---|---|---|
| Медсестра (NURSE-01, палата 101) | `BADGE-1001` | `1111` |
| Старшая медсестра | `BADGE-1010` | `1010` |
| Приёмное отделение | `BADGE-2001` | `2001` |
| Персонал | `BADGE-3001` | `3001` |

После 5 неверных PIN бейдж блокируется на 5 минут: пятая ошибка отвечает 401, дальше до конца блокировки — 429 с `Retry-After`, даже при правильном PIN. Счётчик и блокировка хранятся в базе (`LoginThrottle`), поэтому перезапуск backend их не сбрасывает; если база недоступна, вход закрыт (503). Сессия хранится в подписанной cookie и действует 12 часов (одна смена).

### Экраны

Разделы открываются из боковой панели слева (на телефоне — из полосы вверху). Там же имя и роль, переключатель светлой и тёмной темы (без выбора тема следует настройке системы), кнопка выхода и состояние сервера и базы.

| Экран | Кто видит | Что можно сделать |
|---|---|---|
| Приёмное отделение | приёмное отделение | госпитализировать нового пациента (или вернувшегося — он находится по телефону), перевести в другую палату, выписать; поиск по ФИО и телефону |
| Пост медсестры | медсёстры, старшая медсестра | активные оповещения своих палат и эскалированные на себя (старшая медсестра видит все), подтверждение, свой статус (принимаю вызовы / занят(а) / не на смене), звук для HIGH и CRITICAL, сводка (активные, критические, эскалированные, подтверждённые за час со средней реакцией), подтверждённые за час с временем реакции; обновляется каждую секунду |
| Отчёт старшей медсестры | старшая медсестра | время реакции (среднее, медиана, максимум, доля подтверждённых за 30 с), число эскалаций, разрез по приоритетам и медсёстрам, история оповещений с фильтрами и журналом каждого оповещения; период — смена, сутки, 7 или 30 дней |
| Палаты | все роли | сводка по отделению (всего мест, занято, свободно, палат без мест) и занятость каждой палаты, без данных пациентов; обновляется раз в 10 секунд |
| Симулятор устройств | медсёстры, старшая медсестра | только для демо: создаёт оповещение от монитора или кнопки вызова в выбранной палате; выключается `MEDBASE_SIMULATOR_ENABLED=false` |

Фоновая эскалация работает в backend ([decisions.md](docs/decisions.md), записи 1, 9 и 12). Каждые 2 секунды она находит неподтверждённые HIGH и CRITICAL: `PENDING` старше 30 секунд и `ESCALATED`, у которых с последней эскалации прошло 30 секунд (повторная эскалация). Оповещение уходит медсестре на смене, которую по нему ещё не звали (назначенной оно не возвращается), в таком порядке:

1. свободная медсестра («принимаю вызовы»): из той же палаты, затем с того же этажа, затем любая;
2. старшая медсестра, если свободна;
3. занятая медсестра той же палаты или этажа — она на смене и рядом;
4. старшая медсестра, если занята;
5. любая другая занятая медсестра.

Медсестра «не на смене» не вызывается никогда. Если на смене не осталось никого, кого ещё не звали, оповещение остаётся у медсестры, к которой пришло последним, и на посту старшей медсестры (она видит все оповещения). `LOW` не эскалируется. Процедура `sp_EscalateAlert` перед записью ещё раз проверяет эти правила. Отключается `MEDBASE_ESCALATION_ENABLED=false`.

### Разработка без Docker для backend и интерфейса

База остаётся в Docker, а backend и интерфейс запускаются локально и перезагружаются при изменениях:

```bash
docker compose up -d --wait db
```

```bash
cd backend
python -m venv .venv
.venv/Scripts/pip install -r requirements-dev.txt
.venv/Scripts/uvicorn app.main:app --reload
```

```bash
cd frontend
npm ci
npm run dev
```

Интерфейс откроется на http://localhost:5173, запросы к `/api` Vite передаёт в backend на порту 8000. На Linux и macOS вместо `.venv/Scripts/` пишется `.venv/bin/`.

Тесты backend (нужна запущенная база):

```bash
cd backend
.venv/Scripts/python -m pytest
```

Тесты, которые меняют данные, перед запуском перезаливают `db/04_seed.sql` от имени владельца базы (`MEDBASE_TEST_ADMIN_URL`, по умолчанию `medbase` / `medbase` на порту 55440). Поэтому после тестов в базе остаётся состояние последнего теста; вернуть исходные данные можно командой из раздела «Типовые действия».

Перед запуском тестов backend остановите контейнер backend (`docker compose stop backend`): его фоновая эскалация меняет оповещения в той же базе, и тесты, которые ждут неэскалированное оповещение, начнут падать. В самих тестах фоновая эскалация выключена.

### База данных

При первом запуске (пустой volume) контейнер базы сам выполнит `db/setup.sql`.

| Параметр | Значение |
|---|---|
| Хост / порт | `localhost:55440` |
| База | `hospital_ward` |
| Пользователь / пароль | `medbase` / `medbase` |
| Контейнер | `medbase-postgres` |

Папка `db/` смонтирована в контейнер как `/db`, поэтому скрипты запускаются прямо оттуда.

**База создана до 19 ноября 2026?** Тогда в ней нет хранения блокировки PIN (T-48), и новый backend не сможет выполнить вход. Есть два способа обновить её:

- пересоздать с тестовыми данными (всё, что введено вручную, пропадёт):

  ```bash
  docker compose down -v
  docker compose up -d --build --wait
  ```

- или сохранить данные и применить добавочную миграцию (подробнее — в [отчёте T-48](docs/testing/login-lockout-report.md)):

  ```bash
  docker compose stop backend
  docker compose exec -T db psql -U medbase -d hospital_ward -v ON_ERROR_STOP=1 -f /db/migrations/20261118_persistent_login_lockout.sql
  docker compose up -d --build --wait backend
  ```

## Доступ к БД из терминала

Через psql внутри контейнера (ничего ставить не нужно):

```bash
docker exec -it medbase-postgres psql -U medbase -d hospital_ward
```

Через psql, установленный на компьютере:

```bash
psql "postgresql://medbase:medbase@localhost:55440/hospital_ward"
```

Полезные команды внутри psql:

| Команда | Что делает |
|---|---|
| `\dt` | список таблиц |
| `\d "Patient"` | структура таблицы |
| `\df` | процедуры и функции |
| `\dv` | представления |
| `\du` | роли |
| `\x` | вертикальный вывод (для широких строк) |
| `\i /db/05_queries.sql` | выполнить файл |
| `\q` | выход |

**Важно:** таблицы и колонки созданы в кавычках, поэтому писать их нужно тоже в кавычках и с тем же регистром:

```sql
SELECT "FullName" FROM "Patient";   -- работает
SELECT FullName FROM Patient;       -- ошибка: relation "patient" does not exist
```

Для GUI-клиентов (DBeaver, DataGrip, pgAdmin) используйте те же параметры из таблицы выше.

## Демо для презентации

Сейчас есть только SQL-демо. Сценарий показа в браузере (госпитализация → сигнал из симулятора → подтверждение или эскалация → отчёт старшей медсестры) готовится в задаче T-43.

```bash
docker exec -it medbase-postgres psql -U medbase -d hospital_ward -f /db/demo.sql
```

Перед стартом демо перезаливает тестовые данные, затем идёт по шагам и ждёт Enter после каждого:

1. таблицы и количество строк;
2. бизнес-запрос «кто сейчас лежит и где» и занятость палат;
3. главное действие: госпитализация;
4. правила процедуры: полная палата, повторная госпитализация, несуществующий пациент;
5. ограничения: `Capacity > 0`, допустимые `Status`, FK, `ON DELETE RESTRICT`, один активный приём;
6. перевод между палатами с автоматическим закрытием старой госпитализации, затем выписка;
7. транзакция: регистрация вместе с госпитализацией и откат при полной палате;
8. оповещения (Lab 04): новое оповещение от монитора, эскалация через 30 с на свободную медсестру, подтверждение, журнал событий и время реакции;
9. роли: что может обычный персонал, приёмное отделение и медсёстры.

Ошибки (`ERROR`) в демо ожидаемые: они показывают, что правила работают. Демо можно запускать повторно.

Если запущен backend, его фоновая эскалация сама эскалирует просроченное ALT-1001 через пару секунд после перезаливки данных. Тогда в шаге 8 ручная эскалация ALT-1001 будет отклонена («was escalated … s ago»). Чтобы показать шаг 8 как задуман, на время SQL-демо остановите backend: `docker compose stop backend`.

## CI

Workflow [`.github/workflows/ci.yml`](.github/workflows/ci.yml) запускается на каждый PR в `main`, на каждый push в `main` и вручную (Actions → CI → Run workflow). Четыре проверки идут параллельно, и все они должны быть зелёными:

| Проверка | Что делает | Как повторить у себя |
|---|---|---|
| `db-check` | `scripts/check-db.sh`: база с нуля, SQL-тесты, демо до конца, `05_queries.sql`, повторный `setup.sql` и тесты ещё раз; затем `scripts/check-backup.sh`: бэкап и восстановление на новом сервере | `bash scripts/check-db.sh`, затем `bash scripts/check-backup.sh` |
| `backend-tests` | поднимает чистую базу (`docker compose up -d --wait db`) и запускает все тесты backend (pytest, 263 теста); отчёт JUnit сохраняется как артефакт запуска | `docker compose up -d --wait db`, затем в `backend`: `python -m pytest` |
| `frontend-build` | `npm ci` и `npm run build`: проверка типов TypeScript и production-сборка | в `frontend`: `npm ci`, `npm run build` |
| `system-start` | `docker compose up -d --build --wait` всей системы (NFR-05), затем через nginx на порту 8080: главная страница, `/api/health` с подключённой базой, вход тестовой старшей медсестрой и отчёт | `docker compose up -d --build --wait` |

Что делает `db-check` по шагам:

1. собирает базу с нуля через `docker compose` (пустой volume);
2. запускает автотесты;
3. прогоняет `db/demo.sql` до конца: ожидаемые ошибки демо допустимы, а сломанный SQL (`syntax error`, `relation ... does not exist` и т. п.) — нет;
4. выполняет `db/05_queries.sql`, повторно запускает `db/setup.sql` и ещё раз тесты;
5. отдельным шагом job — `scripts/check-backup.sh` (см. [Резервное копирование](#резервное-копирование-t-44)).

**Внимание:** `check-db.sh` пересоздаёт локальную базу (`docker compose down -v`), поэтому данные, введённые вручную, пропадут. Тесты backend перезаливают тестовые данные перед каждым тестом; запускайте их только на локальной базе. Перед ними остановите контейнер backend (`docker compose stop backend`): его фоновая эскалация меняет те же данные.

## Типовые действия

```bash
# Пересоздать схему и данные заново
docker exec medbase-postgres psql -U medbase -d hospital_ward -f /db/setup.sql

# Только перезалить тестовые данные
docker exec medbase-postgres psql -U medbase -d hospital_ward -f /db/04_seed.sql

# Бизнес-запросы
docker exec medbase-postgres psql -U medbase -d hospital_ward -f /db/05_queries.sql

# Автотесты (176 проверок, в конце "ALL TESTS PASSED", данные не меняются)
docker exec medbase-postgres psql -U medbase -d hospital_ward -v ON_ERROR_STOP=1 -f /db/tests/test_hospital_ward.sql

# Остановить / удалить контейнер вместе с данными
docker compose stop
docker compose down -v
```

Тесты рассчитаны на состояние после `04_seed.sql`.

### Резервное копирование (T-44)

```bash
# Создать резервную копию БД в папку backups/
bash scripts/backup-db.sh

# Восстановить БД из файла резервной копии (пересоздаёт базу)
bash scripts/restore-db.sh backups/<имя_файла>.sql

# Проверить полный цикл: бэкап → восстановление на новом сервере → данные и права
bash scripts/check-backup.sh
```

- В дампе данные пациентов и bcrypt-хэши PIN. Файл и новая папка создаются с правами только для владельца (`umask 077`); `backups/` в `.gitignore`, но это не защищает файл на диске — не передавайте дамп и не храните его в общих папках.
- `pg_dump` не сохраняет роли кластера (`medbase_api`, `medbase_nurse` и т. д.). Поэтому `restore-db.sh` сначала выполняет `db/00_roles.sql`, а потом загружает дамп с его правами. На новом сервере роль `medbase_api` создаётся с паролем для локальной разработки.
- `check-backup.sh` восстанавливает в отдельный временный контейнер PostgreSQL без ролей, проверяет таблицы, данные, членство в ролях, `SET LOCAL ROLE` и то, что PublicStaff не читает `Patient`. Отрицательные контроли (удалённое представление, лишний GRANT) должны валить проверку. Рабочая база только читается. Скрипт выполняется в CI (job `db-check`).

## Что реализовано (база данных v2)

База — второй, независимый слой защиты: даже если backend ошибётся, процедуры, ограничения и права не дадут записать некорректные данные ([decisions.md](docs/decisions.md), запись 5).

**Коечный фонд (Task 09)**

- **Таблицы:** `Patient`, `Ward`, `Admission` (связующая M:N).
- **Правила:** `Capacity > 0`, `WardType` — только из списка, `DOB` обязательна, `Phone` уникален, `Status` — только `Active` / `Discharged`, у закрытой госпитализации есть `DischargeDate` не раньше `AdmitDate`.
- **Внешние ключи** `ON DELETE RESTRICT`: нельзя удалить пациента или палату, у которых есть история госпитализаций.
- **Один активный приём на пациента** — уникальный индекс `UX_Admission_OneActivePerPatient`.
- **`sp_AdmitPatient(patient, ward)`** — госпитализация с проверкой вместимости. Если пациент уже лежит в другой палате, это перевод: старая госпитализация закрывается (`Discharged`). Строки палаты и пациента блокируются, поэтому две параллельные госпитализации не займут одну последнюю койку.
- **`sp_RegisterAndAdmitPatient(name, dob, phone, gender, ward)`** — транзакция: регистрация пациента (если его нет, поиск по телефону) + госпитализация. Если палата заполнена, регистрация откатывается.
- **`sp_DischargePatient(patient)`** — выписка: закрывает активную госпитализацию.

**Оповещения медсёстрам (Lab 04 — Task 07, [decisions.md](docs/decisions.md), запись 1)**

- **Таблицы:** `Nurse` (бейдж, PIN только в виде bcrypt-хэша, статус `Available` / `Busy` / `OffShift`), `NurseAssignment` (кто работает в какой палате, одна основная медсестра на палату), `WardAlert`, `AlertEvent`.
- **`WardAlert`** хранит отдельно назначенную медсестру, медсестру эскалации и подтвердившую медсестру, а также время создания, эскалации и подтверждения. По ним считается время реакции. Ограничения не дают сохранить несогласованное оповещение (подтверждено без медсестры, эскалирован `LOW` и т. п.).
- **`AlertEvent`** — журнал событий (`CREATED`, `ASSIGNED`, `ESCALATED`, `ACKNOWLEDGED`). Его заполняет триггер на `WardAlert`. Триггер `TR_AlertEvent_AppendOnly` запрещает `UPDATE` и `DELETE` всем, включая владельца базы; от администратора, который может отключить триггер, это не защищает.
- **`sp_RaiseAlert(ward, patient, source, priority, description, nurse, NULL)`** — создаёт оповещение и возвращает его номер (`ALT-…`). Проверяет, что пациент лежит в этой палате, а медсестра работает в ней и на смене.
- **`sp_EscalateAlert(alert, nurse)`** — эскалация `HIGH` / `CRITICAL`: `PENDING` не раньше чем через 30 с после создания, `ESCALATED` (повторная) не раньше чем через 30 с после прошлой эскалации; только на медсестру на смене, не назначенную и которую по этому оповещению ещё не звали; `Busy` — только если не осталось свободной (`decisions.md`, запись 12).
- **`sp_AcknowledgeAlert(alert, nurse)`** — подтверждение: назначенной медсестрой, медсестрой эскалации или медсестрой этой палаты. Назначенная медсестра при этом не затирается.
- **`sp_SetNurseStatus(nurse, status)`** — смена статуса медсестры.
- **`sp_SetNurseLocation(nurse, ward)`** — где медсестра сейчас: считыватель бейджа у двери палаты или отметка на посту; эскалация зовёт ближайшую, карта отделения показывает (`decisions.md`, запись 14).
- **Тестовые медсёстры и их PIN** перечислены в начале [db/04_seed.sql](db/04_seed.sql).

**Роли**

- `medbase_admissions` (врачи и приёмное отделение) — пациенты, госпитализации, выписка.
- `medbase_public_staff` — только `vw_WardCapacity` (занятость палат без данных пациентов).
- `medbase_nurse` — читает оповещения, подтверждает их, меняет свой статус.
- `medbase_head_nurse` (старшая медсестра) — всё, что может медсестра, плюс отчёт `vw_AlertResponse` (время реакции и эскалации по каждому оповещению, без данных пациентов) и журнал `AlertEvent`.
- `medbase_alert_service` (фоновая эскалация и симулятор устройств) — создаёт и эскалирует оповещения; из журнала `AlertEvent` читает только, кого уже звали.
- Процедуры закрыты от `PUBLIC`. Писать в `WardAlert` и `AlertEvent` напрямую не может ни одна роль, а хэши PIN никто, кроме владельца базы, не читает.
- `medbase_api` — роль, под которой подключается backend. Сама по себе она не видит данных: на каждый запрос backend переключается (`SET LOCAL ROLE`) в роль вошедшего пользователя, и база ещё раз проверяет его права.

**Вход**

- **`StaffAccount`** — учётные записи сотрудников, которые не медсёстры (приёмное отделение, персонал). Медсёстры входят по бейджу и PIN из `Nurse`. Один бейдж принадлежит ровно одному человеку в обеих таблицах.
- **`fn_LoginStaff(badge, pin, …)`** ([06_login_security.sql](db/06_login_security.sql), T-48) — единственная функция входа, доступная `medbase_api`. Блокирует строку бейджа, по часам базы проверяет блокировку, сверяет PIN с bcrypt-хэшем и обновляет счётчик ошибок — всё в одной транзакции, поэтому параллельные запросы не обходят лимит. Хэши PIN не покидают базу.
- **`LoginThrottle`** — бейдж, число ошибок, срок блокировки. PIN, хэшей и данных пациентов в ней нет. Прямого доступа к таблице у `medbase_api` нет.
- Прежняя `fn_AuthenticateStaff` остаётся только для владельца базы; `medbase_api` её выполнить не может.

## Ручная проверка параллельной госпитализации

Автотест не может открыть две сессии, поэтому проверка вручную в двух терминалах.
После `04_seed.sql` в палате 101 нет свободных мест, а в палате 103 свободны 3 места. Займите два из них, чтобы осталось одно:

```sql
-- Терминал 1
CALL sp_AdmitPatient(5, 103);
CALL sp_AdmitPatient(6, 103);
BEGIN;
CALL sp_AdmitPatient(7, 103);   -- последнее место, транзакция пока открыта

-- Терминал 2 (зависнет, ожидая терминал 1)
CALL sp_AdmitPatient(8, 103);

-- Терминал 1
COMMIT;
-- Терминал 2 получит: ERROR: Ward ID 103 is full (Capacity: 3, Occupied: 3).
```

После проверки верните данные: `\i /db/04_seed.sql`.
